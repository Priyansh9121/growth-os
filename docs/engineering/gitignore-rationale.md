# .gitignore Rationale

**Status:** Current as of 2026-08-15
**Verified by:** `npm run verify:gitignore` ([scripts/verify-gitignore.mjs](../../scripts/verify-gitignore.mjs))

Every significant ignore rule, justified. For each: what it hides, why,
whether it is generated, whether it can contain secrets, whether it is
machine-specific, whether it can be reconstructed — and, critically, whether a
similarly-named _application_ directory could be caught by it.

---

## The rule that governs this file

> **Anchor any pattern whose name could plausibly collide with first-party
> source.**

An unanchored pattern like `models/` matches at **every depth**. It would
silently swallow `packages/database/src/models/`. The author sees a clean
working tree, commits, and the code is simply absent from the repository —
usually discovered by a colleague cloning it days later.

`/models/` matches only the repository root. When in doubt, anchor.

## This was not hypothetical

The verifier caught two real instances of exactly this bug in this repository's
first `.gitignore`:

| Original rule | Would have hidden                                                                | Fixed to                                                   |
| ------------- | -------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| `coverage/`   | `packages/seo/src/coverage/` — **keyword coverage is a planned Stage 6 feature** | `/coverage/` + `apps/*/coverage/` + `packages/*/coverage/` |
| `out/`        | `packages/integrations/src/out/` — outbound webhooks                             | `/out/`                                                    |

Both were caught _before_ those directories existed, which is the only time
catching them is cheap. That is what `verify-gitignore.mjs` is for.

## Category: dependencies

```
node_modules/   .pnp   .pnp.*   .yarn/cache/   .yarn/install-state.gz
```

| Question          | Answer                                                          |
| ----------------- | --------------------------------------------------------------- |
| Generated?        | Yes — by `npm install`                                          |
| Secrets?          | No, but can contain a `.npmrc` with a registry token            |
| Machine-specific? | Yes — native bindings (`@node-rs/argon2`) are platform-compiled |
| Reconstructible?  | Exactly, from `package-lock.json`                               |
| Collision risk?   | **None.** No plausible source directory is named `node_modules` |

Unanchored deliberately: nested `node_modules` are normal in a monorepo.

## Category: build output

```
.next/   /out/   apps/*/dist/   apps/*/build/   packages/*/dist/   packages/*/build/
*.tsbuildinfo   next-env.d.ts
```

| Question          | Answer                                                                                              |
| ----------------- | --------------------------------------------------------------------------------------------------- |
| Generated?        | Yes                                                                                                 |
| Secrets?          | **Potentially.** A build inlines `NEXT_PUBLIC_*` values, and a misconfigured build could embed more |
| Machine-specific? | Yes — absolute paths appear in source maps                                                          |
| Reconstructible?  | Yes, via `npm run build`                                                                            |

**Collision handling.** `/dist/` and `/build/` are deliberately **not** used
unanchored — a future `packages/ui/src/build/` (token build helpers) must
survive. They are scoped per workspace instead. `.next/` is safe unanchored
because a leading dot cannot collide with a source directory. `/out/` is
anchored, as noted above.

`next-env.d.ts` is regenerated by Next.js on every build and only ever
produces merge conflicts.

## Category: environment & secrets — **the highest-stakes rules**

```
.env
.env.*
!.env.example
!.env.*.example

*.pem  *.key  *.p12  *.pfx  *.keystore  *.jks
secrets.json  service-account*.json  gha-creds-*.json
```

| Question          | Answer                                                       |
| ----------------- | ------------------------------------------------------------ |
| Generated?        | No — authored, or issued by a provider                       |
| Secrets?          | **Yes. This is the category that ends companies**            |
| Machine-specific? | Yes                                                          |
| Reconstructible?  | No. Must be recoverable from a secrets manager, not from git |

**Deny-then-allow.** `.env.*` denies everything, then `!.env.example` re-allows
the documented template. Order matters: in `.gitignore`, the _last_ matching
pattern wins, so the negations must come after the deny.

**Collision risk — checked.** Could `.env.*` catch application source? A file
named `.env.config.ts` would be caught. The verifier probes
`packages/config/src/env.config.ts` (no leading dot) to confirm normal
environment-handling _modules_ remain trackable. Only dotfiles are affected,
and a dotfile named `.env.something` is a config file by convention.

**Credential extensions are unanchored on purpose.** A `.pem` anywhere is
wrong. The cost of over-matching is one `git add -f` for a legitimate test
fixture; the cost of under-matching is a leaked private key.

## Category: test, coverage & profiling artefacts

```
/coverage/   apps/*/coverage/   packages/*/coverage/
.nyc_output/   /playwright-report/   /blob-report/   /test-results/
.playwright/   /lighthouse/   *.cpuprofile   *.heapsnapshot
```

| Question          | Answer                                                                                                                                                      |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Generated?        | Yes — by `npm test` / `npm run e2e`                                                                                                                         |
| Secrets?          | **Yes, indirectly.** A heap snapshot can contain live session tokens and passwords from process memory. Playwright traces can contain authenticated cookies |
| Machine-specific? | Yes                                                                                                                                                         |
| Reconstructible?  | Yes, by re-running                                                                                                                                          |

**Anchored** after the `coverage/` incident above. `.nyc_output/` and
`.playwright/` are dot-prefixed and safe unanchored.

## Category: local database state

```
/pgdata/   /.dev-db/   *.sqlite   *.sqlite3   *.db-journal
*.dump   *.sql.gz   /dumps/
```

| Question          | Answer                                                                            |
| ----------------- | --------------------------------------------------------------------------------- |
| Generated?        | Yes — by a local database or a backup tool                                        |
| Secrets?          | **Yes.** A dump of any real environment contains customer PII and password hashes |
| Machine-specific? | Yes                                                                               |
| Reconstructible?  | Locally yes (`db:migrate` + `db:seed`); a production dump, never                  |

`/pgdata/` is anchored so `packages/database/src/data/` would survive. Dump
extensions are unanchored — a database dump has no business anywhere in this
repository.

## Category: logs

```
*.log   npm-debug.log*   yarn-debug.log*   yarn-error.log*   /logs/
```

| Question         | Answer                                                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------- |
| Generated?       | Yes                                                                                                                                      |
| Secrets?         | **Yes.** Logs routinely capture request bodies, session identifiers and tokens — the reason redaction is centralised in the audit writer |
| Reconstructible? | No, and they should not be                                                                                                               |

`/logs/` is anchored so a future `packages/observability/src/logs/` module
survives. That path is one of the verifier's probes.

## Category: caches

```
.cache/   .turbo/   .eslintcache   .stylelintcache   .vitest/   .swc/
```

Generated, machine-specific, reconstructible, no secrets. All dot-prefixed, so
no collision risk.

## Category: large binary assets

```
/model-weights/   *.gguf   *.safetensors   *.onnx   *.ckpt
/screenshots/   /.debug/
```

Not reconstructible from source, but they do not belong in git history —
committing a multi-gigabyte weights file is effectively irreversible.

**Collision handling — the important one.** The directory is
`/model-weights/`, **not** `models/`. `models/` would be the natural name and
would swallow `packages/database/src/models/` and `apps/voice/src/models/`
(turn-detection _code_, not weights). Both are verifier probes. Weight _files_
are matched by extension instead, which is precise.

## Category: editor & OS metadata

```
.DS_Store  ._*  .Spotlight-V100  .Trashes  Thumbs.db  ehthumbs.db  desktop.ini
.idea/  *.iml  *.swp  *.swo  *~
.vscode/*  !.vscode/settings.json  !.vscode/extensions.json  !.vscode/launch.json
```

Machine-specific noise. VS Code uses deny-then-allow so _shared_ workspace
configuration stays tracked while personal state does not.

`._*` (macOS AppleDouble files) is the one rule with real collision potential —
it would catch a source file beginning with `._`. No such convention exists in
JavaScript or TypeScript.

## Verification

Run after any change to `.gitignore`:

```bash
npm run verify:gitignore
```

It asserts three properties:

1. **No existing first-party source is ignored** — via
   `git ls-files --others --ignored --exclude-standard` under each source root.
2. **Twelve plausible future source paths remain trackable** — the paths most
   likely to collide with a careless pattern. This is the check that matters,
   because it fires _before_ the directory exists.
3. **Nothing dangerous is tracked** — no `.env`, key material, model weights,
   dumps, logs, `node_modules` or build output. Plus: `.env.example` is _not_
   ignored, and `.env` / `.env.local` _are_.

Manual commands for ad-hoc investigation:

```bash
git check-ignore -v path/to/file      # which rule matches, and where it is defined
git status --ignored                  # everything currently ignored
git ls-files                          # everything currently tracked
```

## If source is accidentally ignored

```bash
git check-ignore -v packages/x/src/y.ts   # find the offending rule
# Anchor or scope the rule in .gitignore, then:
git add -f packages/x/src/y.ts            # force-add the already-hidden file
npm run verify:gitignore                  # confirm the fix
```

Then add the path to `PROBES` in `scripts/verify-gitignore.mjs`, so the same
mistake cannot recur.
